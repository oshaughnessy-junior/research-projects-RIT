# Pilot contract inventory

## Status and claim boundary

This is a Phase 0 inventory for owner review. It is not evidence that current
RIFT and `sim_manager_supernu` revisions are compatible. The included schemas
are small proposed representations written to exercise the protocol; they were
not extracted from, generated by, or round-tripped through production archives.
Accordingly the real edge is marked `inventory_only` and always reports
`indeterminate`.

## Proposed pilot edge

- Group: `rift-supernu`
- Producer: `supernu-manager`
- Consumer: `rift-hyperpipe`
- Contract: `costly-simulation-evaluation-result`, provisional
  `inventory-0`
- Accountable scientific owners: `coding-rift` together with the
  `sim_manager_supernu` maintainers
- Compatibility commitment: observation only; no RIFT or SuperNu API, CLI,
  archive, default, or campaign behavior changes

The proposed record minimally identifies an evaluation, its parameter mapping,
terminal state, and provenance. Before the edge can become `verified`, its
owners must inventory the actual producer and consumer entry points and record:

1. exact parameter names, coordinates, transformations, and units;
2. request/result status vocabulary and partial-failure behavior;
3. likelihood or objective normalization and numerical uncertainty;
4. canonical content-identity rules and provenance fields;
5. one sanitized artifact produced and consumed by the real code at pinned
   immutable revisions; and
6. an incompatible seeded fixture that the same check detects.

The likely direction—SuperNu manager produces an evaluation result that a RIFT
or HyperPipe adapter consumes—is itself provisional. Owner review may split the
boundary into request and result edges or reverse a producer relationship. That
is a registry correction, not a reason to generalize the core.

## Disconnected demonstration group

`synthetic-protocol-runner` is deliberately unrelated to the scientific pilot.
It verifies that one registry can represent disconnected project groups and
that protocol/code and runner deployment are separate nodes. Its fixtures are
synthetic and are the only `verified` contract in the example registry.
